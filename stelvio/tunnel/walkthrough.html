A self-contained, interactive guide derived from the walkthrough in feature/documentdb-vpc-v1. Current code is the authority. Historical acceptance is distinguished from validation of this revision.

The architecture

Two independent paths share a local handler. AppSync carries invocations and responses. Traforo carries database TCP; a Python relay handles private DNS.

Invocation plane

Public Function URL → Lambda stub → AppSync Events WSS → local bridge → local handler → correlated result back

Database plane

Handler socket → macOS route/utun → root helper → Unix datagram carrier → nonroot Traforo forwarder → SOCKS5/OpenSSH → plugin SSM WSS → SSM agent → loopback sshd → DocumentDB

Private DNS plane

getaddrinfo → macOS scoped resolver → local Python DNS relay → SOCKS/SSH TCP → VPC resolver (+2)

Control plane

CLI → isolated Python networking child → per-VPC supervisors. A launchd root helper owns host mutations and journals. One packaged Go+cgo executable serves two processes: helper and forwarder.

Only explicit bastions: False/omitted warns and runs without managed networking. True/config/dict creates a persistent bastion through deploy. No temporary stack, replacement instance or AWS recover workflow.

Try admission

Host routing also affects other local processes targeting enabled CIDRs. There is one machine-wide helper lease. Overlapping enabled CIDRs and conflicting DNS ownership are rejected. General UDP, ICMP and IPv6 forwarding are outside this implementation.

Complexity from first principles
Each adapter follows a requirement. Removing a requirement can remove machinery; it also changes the contract.
Why sockets → packets → SOCKS → SSH → SSM?
The application creates normal sockets. Transparent host routing exposes IP packets at utun. OpenSSH dynamic forwarding consumes streams, so tun2socks translates packets back into TCP connections. SSH authenticates and opens dynamic remote sockets. SSM supplies the byte carrier without public SSH ingress. WSS is the AWS plugin’s data transport. The Unix carrier keeps raw utun authority inside the small privileged helper.
These are consequences of combining transparent clients, private DNS, no public SSH ingress, and a narrow root boundary. They are not all necessary for one manually configured database client.

Compared with ssh-over-ssm
ssh-over-ssm supplies SSH access over SSM and reduces inbound-port exposure. That transport idea corresponds to Stelvio’s OpenSSH/ProxyCommand/plugin/agent segment. It does not by itself supply transparent packet routing, scoped private DNS, topology discovery, readiness admission, or Stelvio’s helper ownership journal. Reusing a transport wrapper would therefore leave most host integration responsibilities.
ssh-over-ssm reference. This comparison concerns architectural scope; no unverified implementation details from that project are asserted.

What would be simpler?
SSM remote-host port forwarding
Smallest for one fixed endpoint: SDK/CLI StartSession plus AWS plugin. Lose transparent host routing and arbitrary member connections unless adding per-endpoint mappings and DNS. Running aws ssm start-session in a thread handles process lifetime, not DNS or crash-safe host ownership.
OpenSSH fixed -L forwards
Fewer moving pieces than TUN/SOCKS when endpoint count is fixed. Replica discovery and original TLS hostnames require careful local mappings. SSM can remain the carrier.
Direct SSH + Go SOCKS/TUN
Removes OpenSSH subprocess and AWS plugin/agent carrier if SSH is public. Similar to the pinned SST path. Trades fewer dependencies for public ingress and in-process SSH implementation.
Existing VPN / sshuttle
Can substantially reduce Stelvio code by delegating routing and DNS. Requires external installation, privileges, policy and cleanup guarantees; support shifts outside Stelvio. A managed VPN can also add recurring AWS cost.
