01 / Architecture

Local execution.
Private network access.

A public Lambda URL invokes code on your computer. That code uses ordinary database sockets to reach DocumentDB inside a VPC.

The key distinction: AppSync WebSockets carry Lambda events and results. A separate host-networking path carries database traffic. Neither the Lambda stub nor AppSync proxies MongoDB operations.

What was added

The VPC work wraps the existing live Lambda bridge with managed access infrastructure, a native host helper, a protected networking subprocess, SSH-over-SSM, a Go packet forwarder, scoped DNS, discovery, readiness checks and recovery.

The design keeps the real connection hostname, TLS verification and replica-set member discovery. It supports multiple non-overlapping VPCs.

Boundaries worth reviewing

The installed helper is C. The packet-forwarding binary is Go and stays nonroot. The Python CLI, AWS clients, OpenSSH and Session Manager plugin stay nonroot too.

Current host support is explicitly pinned to macOS 15.7.5 arm64 / Darwin 24.6.0. General packet forwarding is IPv4/TCP; local UDP/TCP DNS uses its own TCP-over-SSH relay. This is not a general-purpose UDP VPN.

03 / SST & comparison

Similar packet path.
Different responsibilities.

SST also separates live invocation forwarding from VPC connectivity. Its inspected tunnel is considerably smaller, with a broader privileged process and a direct public SSH connection.

SST local source snapshot · not a live SST deployment

SST’s live Lambda bridge connects to AppSync Events over WebSockets. Its Go cloud runtime reads Lambda Runtime API invocations. The local server provides Runtime API endpoints to separate worker processes, then forwards their results and errors back. Messages are chunked for transport.

Its VPC tunnel

On macOS, installation copies the executable to /opt/sst/tunnel and creates a sudoers grant. The installed process creates utun69, adds subnet routes, runs tun2socks and serves a SOCKS proxy on 127.0.0.1:1080. Its Go SSH client dials the bastion’s public IP directly.

Why the size differs: the short TUN → SOCKS → SSH path is only part of Stelvio’s scope. The implementation also owns temporary AWS resources, scoped DNS, credential isolation, identity checks, per-VPC admission and crash recovery. Fewer source lines alone do not establish equivalent behavior.

Where ssh-over-ssm fits

The ssh-over-ssm project is a transport helper. It prepares a key, uses AWS-RunShellScript to add the public key to the remote user’s authorized keys, schedules removal after 15 seconds, then starts AWS-StartSSHSession. OpenSSH can provide local forwarding or SOCKS.

Stelvio uses the same SSH-over-SSM mechanism, but sends ephemeral public keys through EC2 Instance Connect and pins the server key retrieved through a fixed SSM identity document. The project’s minimum SSH configuration disables strict host-key checking; Stelvio enables it.

That script does not supply TUN interfaces, transparent socket routing, scoped DNS, resource discovery, access provisioning or dev-session recovery. It can replace transport glue, not the whole networking layer.

05 / Simpler solutions

Which requirements
can you relax?

A shorter implementation is possible. The choice depends on whether we need one reachable endpoint or the full transparent, managed workflow.

Keep only the constraints you need

Select requirements to expose gaps. Assessments are architectural proposals, not deployment results or quantified cost estimates. “Needs work” does not mean impossible.

Why a thread running SSM is insufficient

aws ssm start-session --target … starts a shell session by default. A thread changes where the blocking call runs; it does not configure local routing or DNS. For one endpoint, use the remote-host port-forwarding document:

# Illustrative command; not executed or tested by this page.
aws ssm start-session \
  --target <ssm-managed-instance-id> \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<cluster-endpoint>"],"portNumber":["27017"],"localPortNumber":["27018"]}'

This still requires an SSM-managed instance that can resolve and reach the database. It forwards one destination. The normal replica-set driver can discover other member names that this local port does not expose. Connecting as localhost also changes the hostname used for TLS verification.

One constrained design keeps the real hostname with a separately managed hostname-to-loopback mapping, changes the local port and uses a direct connection. That preserves a possible route to strict TLS but sacrifices the normal discovery/failover behavior. Disabling certificate or hostname checks is not part of the proposed MVP.

AWS documents remote-host forwarding and warns against replica-set mode through a single DocumentDB SSH endpoint forward. See the external references in Evidence.

A simpler starting point

For a single-database MVP: require a persistent managed instance, supervise one SSM remote-host forward, document direct-connection limitations and solve TLS hostname handling explicitly.

For unchanged application code and member discovery: prototype an existing VPN or sshuttle before maintaining a custom host network stack. A VPN moves routes, DNS and authorization into an external networking setup. sshuttle moves much of the implementation into a dependency, but still needs local privilege and remote Python execution.

Switching to AWS CLI session startup alone saves a small portion of Stelvio’s code. It does not remove host routing, DNS, discovery, readiness, ownership or cleanup requirements.

Where simplicity is actually available

Smaller scope: a fixed endpoint, direct client, persistent managed instance and supervised SSM forward removes packet translation, dynamic SOCKS/SSH and most provisioning machinery. It gives up the accepted unchanged-client/discovery and temporary-lifecycle contract.

Same networking behavior, external ownership: a configured VPN with correct split DNS can replace much of Stelvio’s tunnel code. AWS routes, authorization, SGs, DNS and lifecycle still exist somewhere. This is less Stelvio code, not necessarily less total system complexity.

Same scope, fewer local adapters: direct SSH-library integration could remove SOCKS/OpenSSH boundaries, or a different small helper language could simplify maintenance. These are experiments, not demonstrated reductions; identity pinning, translation, revocation and cleanup still need implementation and proof.

Actual starting recommendation: if full requirements remain, first measure whether process/adapter consolidation reduces code and recovery states without enlarging root authority. If a reduced MVP is acceptable, explicitly remove the relaxed requirements before choosing a one-port forward. Do not claim this implementation is uniquely minimal.

07 / Stelvio vs SST

Simpler core.
Broader managed contract.

SST’s inspected tunnel consolidates the network path. Stelvio adds explicit DNS, multi-VPC, privilege and temporary-lifecycle guarantees. Neither is a universal winner.

The useful comparison is scope for complexity. Both use TUN → TCP translation → SOCKS → SSH for transparent sockets. Stelvio adds the SSM carrier and a bounded privileged helper; it also implements obligations outside the forwarding path. SST’s direct SSH core is simpler, its tunnel source spans more platforms, and its AppSync boundary uses SigV4. Stelvio’s extra guarantees have real implementation and operational costs.

When the SST-style model is the simpler fit

One selected access path, standing bastion infrastructure, already-working DNS, acceptable direct SSH connectivity, and fewer local process/privilege boundaries. Broader platform source is also useful. Adapt host-key verification and exposure policy deliberately rather than copying the inspected defaults.

When Stelvio’s extra machinery earns its cost

Default automatic temporary access, private-zone DNS, unchanged replica-set clients, simultaneous distinct VPCs, independent failure/admission, no public SSH, and keeping app/credential/network code outside root. These are explicit requirements here, not necessities for every development tunnel.

The tradeoff we chose

Stelvio optimizes for managed behavior and bounded privilege. It spends code, processes, assets, AWS API calls and recovery states to deliver that contract. C plus Go plus Python plus OpenSSH/plugin is a maintenance burden, even though each boundary has a purpose.

SST’s inspected tunnel optimizes for consolidation. Direct SSH and Go integration remove transport adapters and temporary-owner machinery from this comparison. Consolidation puts more network code in the privileged process and assumes a different exposure/DNS/lifecycle setup. Its IAM-signed invocation bridge and broader platform code are strengths beyond this tunnel comparison.

Our next simplification decision: first ask whether temporary lifecycle, private DNS or multi-VPC guarantees can be removed. If all remain, experiment with adapter consolidation while retaining the nonroot boundary, identity checks and existing acceptance gates. An external VPN can reduce Stelvio code but delegates—not erases—routing, DNS and access ownership.

No numerical LOC/performance/cost ranking or general security verdict is asserted. Claims about SST are scoped to inspected files/configuration, not every SST deployment or current upstream behavior.
